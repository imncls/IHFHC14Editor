# Game data: IHF Handball Challenge 14 (Steam, 2014)

Technical reference of what has been found out about the game. Complements `AGENTS.md`, which remains the source of truth for the project rules. Points that are still unchecked in the game are marked as untested.

## Environment
- 64-bit Windows. The game (`HC14.exe`) is 32-bit, so its `sqliteencrypt.dll` only loads into a 32-bit process (a 32-bit Python or a 32-bit helper executable). A 64-bit process cannot load it.
- Local paths on each machine (not versioned): game installation `<GAME_PATH>` and 32-bit Python `<PYTHON32_PATH>`.
- Data the game actually reads: `C:\Users\<user>\Documents\neutron games\HandballChallenge14\save\`, with `handball.challenge.metadata.dump.v13.0.0` and `hc.metadata.stats.dump.v13.0.0`.
- `Data\Database\NG_HC.db` and `NG_HC_STAT.db` look like templates: the game recreates them if they are deleted.
- League saves: `<Documents>\neutron games\HandballChallenge14\SGT_LEAGUE.<n>.sg`, plain XML: `SaveGame(id, name, playerTeamID, leagueID, progress, ...)` plus the fixture list (`MatchTemplate(matchDay, homeTeam, guestTeam)`). They store team ids only, no player data, so a league saved before an edit shows the edited players and rosters when loaded (checked with a transfer). Restoring the database does not touch them.
- Careers and profiles: `handball.challenge.profile.v13` (about 17 KB) is not a SQLite file and does not open with the key.
- `hc.metadata.stats.dump.v13.0.0` holds only per-career statistics (`player_statistics_per_match`, `player_statistics_per_tournament`, `season_statistics`, `career_season_statistics`, `career_statistics`) keyed by `savegame_id`, `player_id` and `team_id`; all empty here. New players need no rows in it.
- The game's logic lives in `HC14.exe`: the Lua scripts in the `.v` files are shader and scene scripts and never touch the database. The executable embeds its SQL, for example team selection by league (`... WHERE league_id IN (SELECT id FROM playerDBLeague WHERE inFinalGame = 1)`, excluding league 15) and its own writes to `playerDBPlayer`, `playerDBPlayerTeam` and `playerDBTeamOutfit`.
- The encryption key (55 bytes, 0x37, in the build analysed) is a plain NUL-terminated string in `HC14.exe`'s `.rdata` (no NUL inside), and exactly one 4-byte aligned pointer in `.data` points to it; the DLL holds no copy. The editor finds it (`app/keyfinder.py`) by trying the `.rdata` strings of 8 to 256 bytes that a pointer in `.data` refers to (a few hundred), then those referred to from anywhere in `.data` or `.text` (about 10,000), each on a copy of the save with the DLL (about 0.2 ms each); the first that opens the data is the key. In this build it takes about 0.3 s in total. It is then saved in `config.local.json` (in `.gitignore`) as hexadecimal and never written to versioned files or logs. Other builds may use a different key, so its length is not checked.

## Finding the game

The game is Steam app `279460`. The editor (`app/steam.py`) reads Steam's folder from the registry (`HKCU\Software\Valve\Steam`, value `SteamPath`), the libraries from `<Steam>\steamapps\libraryfolders.vdf` (its `"path"` entries, backslashes doubled), and in each library `steamapps\appmanifest_279460.acf`, whose `"installdir"` (`IHF Handball Challenge 14`) is the folder under `steamapps\common`. A folder counts only if it holds `SQLiteEncrypt.dll`. The save data is in `<Documents>\neutron games\HandballChallenge14\save` (Documents as Windows reports it, also when redirected to OneDrive).

## Opening the database
- It is an encrypted SQLite database. It is opened with the `sqlite3_open`, `sqlite3_key`, `sqlite3_exec` and `sqlite3_rekey` functions of the game's DLL, loaded with `ctypes.CDLL` from a 32-bit process.
- Flow: copy the encrypted file, decrypt the copy with `sqlite3_rekey(db, None, 0)`, edit the plain copy with the standard `sqlite3`, encrypt it again with `sqlite3_rekey(db, KEY, len(KEY))` and verify by opening it with the key and querying `sqlite_master` (rc 0 and tables).
- `sqlite3_exec` returns 26 (`SQLITE_NOTADB`) if the key or the encryption do not match. If the DLL does not export `sqlite3_rekey`, the data can be edited with `UPDATE` through `sqlite3_exec` and the file stays encrypted.
- How the key was first obtained, before `app/keyfinder.py`: a breakpoint on `sqlite3_key` with x64dbg; the key separators are single bytes (`DF` and `A7`), not UTF-8, and the value `00000037` is hexadecimal.
- DB Browser for SQLite does not open the original, but it does open the plain copy.
- Implemented in `app/gamecrypto.py`; command line `python -m app` (see `CONTRIBUTING.md`).
- The game's `.v` files (BaseData, models, scenes, guiportraits, guiassets) are ZIP files with every byte XORed with 0x55. They contain models, textures, portraits, scenes and Lua scripts, not player data.
- `guiportraits.v` (about 37 MB, 1329 entries, all deflate): `gui/images_fullprice/portraits/` holds 1009 files, mostly `portrait_<player_id>.png` (130x158 PNG; 1006 ids, for example `portrait_223.png` for player 223) plus `no_picture.png`; the rest are team, country and league logos (`.dds` and `.png`). Confirmed in the game: the portrait is chosen by player id (replacing `portrait_256.png` changed Sorhaindo's picture on the lineup screen's player card). A rebuilt archive (same entries, deflate) loads fine.
- `player_img` values in `playerDBPlayerData` (for example `RAUL_ENTRERRIOS_001.jpg`) match no file in `guiportraits.v`, so the field looks unused by the game.
- Portrait formats: 130x158 PNG, 8 bits per channel (549 RGBA, 336 RGB, 121 indexed; three are a few pixels smaller). Three entries break the naming pattern and are probably ignored by the game: `portrait1320.png`, `Portrait_165.png`, `potrait_139.png`. The editor writes `portrait_<id>.png` and replaces an entry that only differs in case.
- How the editor handles portraits (`app/portraits.py`): the installed archive is always the original (backed up once, with its hash, in `backups/original/`) plus the custom portraits in `work/portraits/<player_id>.png`. Apply rebuilds it from the original and installs it atomically; restore installs the original; reload rebuilds `work/portraits` from what is installed. Photos are centre-cropped and resized to 130x158 RGBA PNG with Pillow.

## Data model
- `playerDBData(id, description, key, type, lookup_type_id)` is the field dictionary. Ids: 1 name, 2 first_name, 3 jersey_nr, 4 dob, 5 main_pos, 6 sec_off_pos, 7 sec_def_pos, 8 throw_arm, 9 star_pot, 10 prone_to_inj, 11 weight, 12 height, 13 to 17 body/hair_colour/hair_style/eye_colour/skin_colour (unused: 0 rows), 18 country, 19 national_team_jersey_nr, 20 player_img. Types: STRING, INT, DATE, LOOKUP, FOREIGN_KEY.
- `playerDBPlayerData(player_id, data_id, value VARCHAR)`, primary key (player_id, data_id). 4239 players, with 14 or 15 rows each (player_img only exists for 1422).
- `playerDBLookupTable(id, value, description, lookup_type_id)`:
  - Type 6, throwing arm: 9 right, 10 left.
  - Type 7, main position and secondary offensive position: 21 N/A, 22 left wing, 23 left back, 24 centre back, 25 right back, 26 right wing, 27 pivot, 28 goalkeeper.
  - Type 8, secondary defensive position: 33 N/A, 35 left wing, 36 left back, 37 left centre block, 38 right centre block, 39 right back, 40 right wing.
  - Types 1 to 5 have no rows.
- Value conventions: LOOKUP fields store the ID; `country` stores `Country.ID`; the date is `d.m.yyyy`, sometimes with a zero-padded month (`11.01.1989`) and sometimes without (`31.8.1990`); `national_team_jersey_nr` can be an empty string; `player_img` is a file name (for example `MOREL.jpg`).
- Name lengths: the longest name in the data is 19 characters and the longest first name 17, but the game showed a 38-character name and a 20-character first name without trouble. On the line-up player card names longer than about 20 characters overlap the jersey number, and the roster list cuts them ("J. M. A. FERNÁNDEZ-VILLAV"). The editor allows up to 40 and warns above 20.
- Observed ranges: height 0 to 212, weight 0 to 179, jersey 0 to 100, star_pot and prone_to_inj 1 to 100. 0 seems to mean "no data". These are soft warnings, not game limits.
- `playerDBPlayer(id, sk_fit, sk_throw, sk_acc, sk_pass, sk_speed, sk_jump, sk_power, sk_mob, sk_block, sk_comp, sk_react, total_avg, total_def_avg, total_off_avg, portraitFile)`: 4239 rows, integer skills from 0 to 100. Only 5 players have everything at 65 (the default value). `portraitFile` is empty for everyone.
- Averages of field players (implemented in `app/averages.py`): each one is a weighted mean of the 11 skills with integer weights, in the order fit, throw, acc, pass, speed, jump, power, mob, block, comp, react, stored as `float32(round(x, 2))`. This reproduces 3589 of the 3592 field players exactly (outliers: ids 723, 1491, 4517).
  - `total_def_avg`, every position: 2,1,1,1,1,2,5,3,5,2,3 / 26.
  - `total_off_avg`, every position: 3,2,3,3,4,2,2,3,1,4,1 / 28.
  - `total_avg` by main position: wings (22, 26) 5,2,5,1,5,3,1,4,1,1,1 / 29; backs (23, 25) 3,5,4,2,1,2,3,1,1,3,1 / 26; centre back (24) 3,3,3,5,2,1,2,3,1,5,1 / 29; pivot (27) 2,1,4,1,3,2,5,3,1,3,3 / 28.
- Goalkeepers (main position 28, 647 players): the three averages are always equal and follow no linear formula of the skills (best fit: median error 0.3, maximum 9). The editor sets them by hand.
- `playerDBTeamAverages(team_id, skill_average)`: 199 rows; the value is the mean of `total_avg` over all the team's players (`playerDBPlayerTeam`), stored as float32.
- Names written to `playerDBPlayerData` in the save dump show on the roster selection screen and in the match (confirmed with player 223, FC Barcelona). Players that are only in the pools (teams 194 and 319, for example player 123) never appear in the game.
- `playerDBPlayerTeam(player_id, team_id)`: 7345 rows. `playerDBTeam`: 219 teams (165 LEAGUE and 54 NATIONAL_TEAM), with fields such as coach, colours, stadium and `sr_*_player_id` (captain, shooter...), which reference players by ID.
- Memberships: every player belongs to at most one club-type team (`LEAGUE`, pool 194 included) and one national-type team (`NATIONAL_TEAM`, pool 319 included): 3106 players have both, 55 only a club, 1078 only a national team. Real rosters have at most 25 players.
- Ids: players are not autoincrement (`playerDBPlayer` and `playerDBPlayerData` use ids 1 to 4517 for 4239 players, with gaps). `sqlite_sequence` holds 338 for `playerDBTeam` and 18 for `playerDBLeague`.
- The engine `Player` table (42 rows) holds blueprints (`StaticPlayer`, `Keeper`, ...), not the database players. The engine creates its 3D entities by these names: renaming them (prefix "Y-") crashes the game while building the main menu (ASSERT in `HC_EntityFactory.cpp`). Never edit it.
- New players work: a player inserted with a new id (max + 1 = 4518) in `playerDBPlayerData` (copied rows, without `player_img`), `playerDBPlayer` and `playerDBPlayerTeam` (Barcelona and pool 319) shows in the roster with his number, can be put in the starting seven and plays on court. Without `portrait_<id>.png` the card shows the default silhouette. Friendly matches do not write to `hc.metadata.stats.dump`.
- How the editor makes players (`create_player`, `duplicate_player` in `app/repository.py`): new id = the highest id in `playerDBPlayer`, `playerDBPlayerData`, `playerDBPlayerTeam` and `Customize_table`, plus 1. A new player gets neutral values (skills 65, centre back, his team's country and first free jersey number) and no `Customize_table` row; a duplicate copies the data rows (without `player_img`), skills, averages, `Customize_table` row and portrait. Both join the chosen team and the pool of the other kind. Checked in the game: both show in Granollers' lineup with their numbers, cards (silhouette for the new one, the source's portrait for the copy) and skills, and both play on court.
- `Customize_table(player_id, muscularity, skin_brightness, skin_color, hairstyle, hairstyle_color, body_hairstyle, beard, beard_color, brow, brow_color, eye_color, single_morphs, multi_morphs)` is the 3D look: 3363 rows, 908 players have none (the game then uses a default look), 32 rows belong to ids that no longer exist. Values are asset names, for example skin `Euro01` or `Northeuro01`, hair `1061_Hair06`, textures such as `black_001.dds` or `augen_braun.tga`, and morph lists like `005_overall_typ3|0.04;031_head_pyramidshape|0.39;`.
- The game's list of valid looks is `XMLData/CharacterCustomizationConfig.xml` in `gfx.v` (read by `app/appearance.py`; it is not valid XML until its comments, which contain `--`, are removed). Lists: `SkinColors` (6), `HairStyles` (NONE, ShortHair, 1061_Hair01..10), `HairStyleColors` (7, `*_001.dds`), `Beards` (NONE, Bart01..07_diff.dds), `BeardColors` and `EyeBrowColors` (blond, dunkel_blond, braun, dunkel_braun, rot), `EyeBrows` (NONE, braue01..05_diff.dds), `EyeColors` (6 `augen_*.dds`), `BodyHairStyles` (NONE, _001..003.dds), shape lists (`BodyTypes`, `HeadShapes`, `EyeShapes`, `NoseShapes`, `ChinShapes`, `EarShapes`, `MouthShapes`; lips are wrongly listed under eyes and ears too) and all morph names. Colour previews: each colour's `texturePath` (for example `gui\images_fullprice\customization\Custom_Hair_Darkbrown.png`) names a 41x26 RGBA PNG swatch in `guimisc.v` (same XOR-zip format as `guiportraits.v`; 24 colours plus `Custom_None.png`); the editor shows them as clickable palettes, read at runtime.
  - Formats: `muscularity` and `skin_brightness` 0 to 1; `single_morphs` is `name|value;` with in practice one non-zero shape per category; `multi_morphs` is `negative|positive|:value!slot;` with slots 1 to 10. The data mostly stores `.tga` names (`Bart02_diff.tga`) and empty strings for "none", while the config uses `.dds` and `NONE`.
  - Checked in the game: changed values (skin, hair and colour, beard, brows, eyes, muscularity, body type) and a new row for a player who had none show in the match presentation, with the config's `.dds` names.
- `playerDBTeam.country_id` uses the same ids as `Country.ID` and the player's `country` field (Barcelona, Granollers and Spain: 195). Pools have countries too (194: 53, 319: 242), which the editor does not give to new players.
- Transfers work by editing `playerDBPlayerTeam` alone: a player moved from Granollers to Barcelona appears in Barcelona's lineup with his number and portrait (and no longer in Granollers), and a player moved from pool 319 to Spain appears in Spain's lineup.
- `playerDBTeam` columns and what the game shows (checked in the game by editing Granollers, see `app/teams.py`):
  - `name` on team selection, the lineup and the side screen; teams are listed by name, so a rename moves the team in the list. `coach` on team selection ("Entrenador") and the lineup card. `abbrev` (3 characters) on the match scoreboard.
  - `rating` is the stars on team selection (0.5 to 5.0 in steps of 0.5; Kiel 4.5, Barcelona 5.0, Granollers 4.0). The attack, defence and total numbers next to them are computed from the players.
  - Tactics (0 to 100, 0 = left end of the slider) are the starting values of the lineup screen's sliders. Attack tab: `off_team_speed` patient build-up - fast, `off_team_1vs1` goals from the back - 1 on 1, `off_plays` free play - set plays, `off_crossing` screens - crossing, `off_passing` short - long passes, `off_tricks` standard - tricky. Defence tab: `def_position` defensive - attacking, `def_helping` man marking - doubling, `def_aggressive` passive - aggressive, `def_holding` neutralise - push, `def_intercept` safe - intercepting. `off_focus` has no slider. The defence formation (6-0, 5-1, 3-2-1) is chosen in the game, not stored here. Pirna has `off_crossing` 546, an outlier.
  - Not checked yet: `home_arena` (0, or `playerDBArena`: 9 small, 10 medium, 11 big, 24 training gym), `floor_type_id` (`playerDBFloorTypes`, 5 floors), `spectators_average` (`playerDBSpectatorAverage`, 7 ranges), `home_colour`/`away_colour` (24-bit integers, 0 in 207 of 219 teams, RGB or BGR unknown), `mascot`, `min_skill_average`/`max_skill_average`, `annual_budget`. The friendly's arena list comes from the engine `Arena` table, not from `home_arena`.
  - Logos: `logoFile` points to `gui\images_fullprice\logos\teams\<name>_logo_<id>.dds` in `guiportraits.v`, 512x512 DXT5 (some DXT3), almost all without mipmaps; the game also loads `<name>_small.dds` (48x48) for the scoreboard. 62 teams have no `logoFile` and show the game's generic `team_logo_none.dds` (seen with BM Sur); one (`touraine.dds`) points to a missing file. Pillow 12 writes DXT5 without mipmaps, which the game shows (checked with a custom logo on team selection and the scoreboard).
  - Kits: `playerDBTeamOutfit(id, team_id, type, texture)`, three rows per team (0 home, 1 away, 2 goalkeeper) pointing to `textures\character\custom_dress\...\*.dds`; 12 teams have none. `TextureCustomization(TeamOutfitID, Type, U1, V1, U2, V2, ResourcePath0..2, Color, ZOrder)` places the numbers and names on each outfit (font, colour, position); 315 of 621 outfits have rows. The game reads kits with `SELECT * FROM playerDBTeamOutfit WHERE team_id = %d AND type = %d`.
  - Leagues: `playerDBLeague.teamCount` does not always match the teams pointing to it (Liga ASOBAL: 16 and 16; Training League 4; most leagues 0). The game lists teams for a friendly by `league_id` among leagues with `inFinalGame = 1` (SQL in `HC14.exe`), so `teamCount` does not limit a friendly; whether league mode uses it is unchecked (see 5.5).
  - Ids: `playerDBTeam` and `playerDBTeamOutfit` are `AUTOINCREMENT` (`sqlite_sequence` 338 and 751); the game writes `playerDBTeamAverages` itself (`REPLACE INTO`).
- Leagues (`playerDBLeague`, checked in the game in 5.5):
  - `name` shows in the friendly and league-mode lists (a renamed league showed everywhere). `country_id` puts the league under that country; the country list only has countries with a playable league (Spain, Rest of the world, International, France, Germany).
  - `inFinalGame = 1` makes a league playable; with 0 it never shows (league 5 with two teams moved in stayed hidden).
  - A new row (`INSERT`, id 19 from `AUTOINCREMENT`) with `inFinalGame = 1` and teams pointing to it shows in friendlies and league mode.
  - Built-in leagues (at least 1 Bundesliga and 4 ASOBAL) use fixed fixture templates of the game: their saves have `genericLeague="false"` and always the original teams (ASOBAL: 16 teams, 240 matches; Bundesliga: 18 teams, 306 matches), whatever `teamCount` says. A team added to such a league shows in friendlies but cannot be chosen in league mode ("GetTournamentTeamByID Failed!" in the log) and is left out of the fixtures.
  - New leagues are generated from the data (`genericLeague="true"`): a double round robin of the teams that point to them (4 teams: 12 matches in 6 rounds; 6 teams: 30 matches in 10 rounds; 16 teams: 240 matches in 30 rounds). The team count must be valid: 5 teams fail ("numTeams is not correct! (5)" in `HC_LeagueMainRound.cpp`), 4, 6 and 16 work; other even counts are untested.
  - Teams and players made with the editor work in a generic league (checked: a team of 14 new players in a 6-team league).
  - `teamCount` and `parentID` changed nothing visible; `logoFile` is NULL everywhere and the five files in `logos/leagues/` are not referenced by the game.
  - The game log `handball.challenge.log` (next to the saves) records these failures; read it when a menu does not react.
  - League mode also has a "Torneo personalizado" (custom tournament) entry, not explored.
  - How the editor uses this (`app/leagues.py`): new leagues are inserted with `inFinalGame = 1`, `parentID = 0`, `teamCount = 0`, skill limits 0 and no logo. A league is "made with the editor" when its id is not in the original data. Teams made with the editor only go into such leagues; checked in the game with a 4-team editor league (12 matches in league mode).
- How the editor makes teams (`create_team` in `app/teams.py`): a copy of another team's row (new id from `AUTOINCREMENT`, so 339 first), with name "New team", abbreviation "NEW", no roles and no `logoFile`; its three outfits with their `TextureCustomization` rows; an averages row with 0; no players and no contests. Custom logos are added to `guiportraits.v` as `custom_logo_<team_id>.dds` and `_small.dds` (never replacing original entries), and `logoFile` points to them. Checked in the game: a team made with the editor (copied from Granollers, 14 new players) shows in Liga ASOBAL with its logo, coach and stars, its lineup has the 14 players, and in the match the scoreboard shows "AMI" with the small logo and the Granollers kit with numbers.
- Team roles (`playerDBTeam.sr_captain_player_id`, `sr_shooter_player_id`, `sr_defense_player_id`, `sr_tricky_player_id`, `sr_7m_shooter`) point to players by id, 0 when empty. In the original data some point to players who are not in that team (for example 64 captains set, only 56 of them members), so the game tolerates it. When the editor moves a player out of a team, it clears the roles of that team that point to him; "Revert player" puts them back.
- Duplicate jersey numbers within a team already exist in 66 teams of the original data; the editor warns about them but allows them.
- Roster size is not limited by the game: Barcelona with 26 players (7 moved from pool 194) and Granollers with 13 both load in team selection and the lineup (the list scrolls; added players can be called up), and a friendly between them starts normally. Real rosters have 4 to 25 players.
- The team ratings shown in the game (attack, defence, total) are computed by the game from the players, not read from `playerDBTeamAverages`: after a transfer they change, and they change again once the matchday squad is set.
- Pools: team 319 "NOT ASSIGNABLE" (national teams, 3670 players) and 194 "Not assigned" (clubs, 541 players). The "(Fake)" test players are only in those pools, not in real rosters.
- National teams: those without a suffix have their own roster (Spain 324, France 91, Germany 65...). The "(Original)" teams have 0 players. There are "(Fake)" variants of Denmark (323) and France (286). Real rosters have 4 to 25 players, most of them 14 to 18.
- Engine tables on court, not yet known whether the match uses them: `Player` (42 rows, with a BluePrint such as `static_player.xml` or `cine_player1.xml`), `Membership` (22 rows), `Team` (the first rows are German clubs) and `FieldPosition` (1 Outside, 3 LeftWinger, 9 GoalKeeper, 11 Custom...).

## League package (`.hc14league`, the editor's own format)

A zip written and read by `app/league_package.py`:

- `manifest.json`: `{"format": "hc14-league", "version": 1, "league": {"name", "country_id"}, "teams": [...], "players": [...]}`.
  - A team: `key` (`t1`, `t2`, ...), `sheet` (the editable fields without roles, as the editor shows them), `country_id`, `annual_budget`, `roles` (role column to player key), `outfits` (`type`, `texture` and the `TextureCustomization` columns without ids) and `logo` (true when it has a custom logo).
  - A player: `key` (`p1`, ...), `team` (a team key), `national_team` (a game team id or null for the pool), `data` (`playerDBPlayerData` by key, without `player_img`), `skills`, `overall` (goalkeepers), `look` (the `Customize_table` row or null), `portrait` (true when the file holds its photo) and `game_portrait` (the id of a game player whose original portrait it uses, or null). A custom photo identical to one of the game's own portraits (a copied player's) is never put in the file: it travels as `game_portrait`, and the importer takes that portrait from its own game (none if missing).
- `portraits/p<n>.png` and `logos/t<n>.dds`, `logos/t<n>_small.dds`: the custom images.

Import checks the structure (allowed entry names only, folder entries ignored, size limits, keys and references; every image is decoded and written again as the editor writes them: portraits as 130x158 PNG, logos as 512 and 48 DXT5 DDS) and every value against the importing game's data: team sheets and players' data with the form's own rules, countries, national teams (unknown ones become the pool), looks against the game's appearance list (a package with looks is refused when that list cannot be read), and kits only with textures and fonts already in the game's data. Then the league, teams, kits, players, looks and roles are written in one transaction; photos and logos follow. Averages are recalculated from the skills (goalkeepers keep their overall); dates are kept as written; empty secondary positions (some goalkeepers in the game's data) become N/A.

Export runs the same checks on what it is about to write, so it refuses what no editor could import (for example a league without teams).
